## Method

| Pass | Question |
|---|---|

| 4 | Which controls pay for themselves — in both directions? |
| 5 | Which seams exist for an offline demo? |

## Pass 5 — demo seams (complete)

**Claim (CLAUDE.md, ADR-0006): `pipeline.build_deps` already accepts an injected client and clock.**
Method: read `pipeline.py:291-298`, `:371`; traced every caller.
Result: **CONFIRMED, with a gap.** `http=` replaces the `build_http_client` call at `pipeline.py:371`,
and the correct construction — `build_http_client(transport=httpx.MockTransport(...))` — leaves
`AllowedHostsTransport` wrapped around the mock (`httpclient.py:95-100`), so the egress gate stays
intact and no socket opens. The gap: **no CLI command passes `http=` or `clock=`** (all nine call
sites in `cli.py` omit both). The seam exists for tests only; a demo needs a composition root.

**Claim: an injected fake clock removes the 3.75 s per-request wait.**
Method: read `ratelimit.py:153` (only sleep), `:243-244` (only time reads), `:47` (`WAIT_SLICE_S=300`),
`:150-151` (heartbeat before each slice).
Result: **CONFIRMED for the fetch path.** `RateLimiter` touches time only through `self._clock`.

**Claim (implied): a fake clock makes the whole flow deterministic.**
Result: **REFUTED.** Twelve sites call `datetime.now(tz=UTC)` directly, outside the `Clock`
protocol — `cli.py:121,647,753`, `config.py:411`, `pipeline.py:787,1348,1357`,
`ui/flow.py:109,144,390,568`, `ui/wizard.py:175`. The load-bearing one is
`pipeline.py:787` (`now = until or datetime.now(tz=UTC)`): with a conventional test epoch,
`aktualizuj` would plan roughly 200 five-day windows at one request each. `update_range` does
accept `until=`, but `wizard.handle_update` has no passthrough.

**Claim: the wizard needs a TTY, so it cannot be driven headlessly.**
Method: read `prompts.py:94-101`, `:165-202`, `wizard.py:70`, `cli.py:198-207`, `:216-222`.
Result: **REFUTED as stated.** `Prompter` is a Protocol and `ScriptedPrompter` already ships **in
the production package**. The TTY gate lives only in `cli.py`. A substituted `Prompter` drives the
flow in-process. What such a run does *not* prove: that a human can read the screens — that is
gate 3, and it is a different question.

**Claim: a local mock server is a viable demo design.**
Result: **REFUTED.** It collides with four layers — `apiprofile.py:99`, `pipeline.py:302-309`
(`HOST_ENVIRONMENT` check), `client.py:131-139`, `httpclient.py:53` — and a TLS variant needs
`verify=False` on top. There is no non-weakening way to do it. Transport injection is the
supported route.

**Standing guard worth knowing before designing:** `tests/resilience/test_egress_allowlist.py:148-154`
asserts that production calls `build_http_client(transport=None)`. A `--demo` branch placed *inside*
`build_deps` turns that test red — correctly. The substitution belongs at the composition root.

### Risks the demo carries

1. **`firma.zrodlo` is `CHECK (zrodlo IN ('CEIDG_API','CEIDG_RAPORT'))`** (`store.py:75`). A seeded
   demo database **cannot label itself synthetic**, so it is indistinguishable from a production one
   — and so is any workbook exported from it. This is the project's own recurring failure shape:
   evidence sanitised of exactly the property that matters.
2. **The token chain.** `DEFAULT_ENV_FILE = Path(".env")` is CWD-relative, so any demo run through
   `cli._settings` loads the owner's real, PESEL-bearing `CEIDG_TOKEN`. Keyring is empty; the
   credentials live in `.env` at the repo root. There is no flag to disable the chain, and adding
   one would put a credential bypass into production code.
3. **`scripts/anonymize_samples.py` does not scrub NIPs from query strings.** `Anonymizer.url`
   (`:183-185`) rewrites host and GUIDs only. `probe_out/mini/06_200_firmy.json` and
   `probe_out/nip_ids/1_200_firmy.json` both carry live `nip=` values today. There is also no
   anonymiser at all for the report CSV or for SQLite.
4. **`.gitignore` covers `*.sqlite *.csv *.xlsx *.jsonl` but not `.json`, `.yaml`, `.ndjson`** —
   so `demo/recordings/*.json` would stage by default into another team's repository.
5. **A new top-level `demo/` directory silently escapes the boundary scans**: the rule-11 and
   rule-12 AST checks cover `ceidg_tool/`, `scripts/`, `tests/` and `./ceidg_probe.py` only
   (`tests/test_boundaries.py:664`, `:887-898`).

### Also measured

- Assistant replay is already solved in principle: SSE bytes over `httpx2.MockTransport` through
  `build_model_http_client(transport=…)` at `tests/test_assistant_caller.py:133-155`; the SDK client
  is built in exactly one place (`assistant/caller.py:142-147`) and takes `http_client=`.
  But **assistant retry sleeps for real** (`caller.py:229`) — `AnthropicCaller` takes no clock.
- `CEIDG_DATA_DIR` (`config.py:42`, `:420-421`) moves store, `wyniki/`, `logi/` and `raporty/`.
- Resume after a kill is fully modelled offline for `pobierz` (`store.py:643-698`, pinned by
  `tests/resilience/test_s1_kill_and_resume.py`). **`aktualizuj` and `raport` runs do not resume
  at all** (`pipeline.py:459-465`, `:493-498`, `cli.py:462-466`) — only the watermark survives.
- `build_deps` has no `store=` parameter.

## Pass 4 — do the controls earn their keep (complete)

**Premise correction, recorded because it changes what evidence means here.** The pass was
briefed to treat git history as primary evidence. It is not: the repository has **6 commits, all
dated 2026-09-08**, and `d6a46e9` is a 157-file initial commit containing phases 0-5. Every defect
but three predates version control. The pass re-based on artifacts present in the tree at a named
line, on `.claude/sessions/*.md` (994 lines — the real defect ledger), and on the closed sections
of `docs/status.md`.

**All 13 ADRs earn their keep.** Strongest entries: ADR-0013 (2 681 requests and 13 401 records
delivering nothing overnight; 15 550 orphans one `wyczysc` away from deletion), ADR-0012 (its own
gate item found that repeated `pkd=` had never been measured as OR, while multi-code queries had
been shipping since phase 4d), ADR-0011 (caught CI never installing the `asystent` extra — the
suite collected on *no* matrix leg). Notable: **ADR-0010's feature was never built and the ADR
still paid for itself**, because writing it split out two live defects — the proxy hole and the
silent 21 MB download.

**Boundary rules 7, 9, 10, 11, 12, 13, 14 earn.** Rule 11 is the highest-value control in the
project: `HTTPS_PROXY` routed every request — PESEL-bearing token included — through an
unvalidated host, because both pre-existing checks read the URL string and not the socket.

**Boundary rules 1-6 and 8: NO ENTRY FOUND — and recommended to keep.** No recorded violation.
Their cost is roughly 50 lines of scan table; the *enforcement* of them has two recorded defects
(relative-import blindness, found twice); and their invisibility is most likely an artifact of
predating version control. Settled cheaply by a one-off planted-import mutation sweep across the
~12 governed modules (~15 minutes) — not by removal.

**Every test cluster earns.** No cluster was assessed as ceremony.

**The one control to positively remove: the 1 076-line retrospective phase log in
`docs/status.md`.** It cannot catch anything, because nothing consults it — one Python citation,
not mechanised, and it is a second copy of the session briefs in another language (the copy that
is *not* auto-loaded at session start). Its only demonstrated effects were two errors it caused
elsewhere. Recommendation: trim to ~190 lines, keeping the live sections and the "Argued against
rather than applied" section, which exists nowhere else.

## Pass 1 — data loss and misrepresentation (complete)

Severity here is the audit's top category: anything that loses data or tells the operator
something untrue about the data. Each finding below was reproduced offline, against the real
`Store` or against real recorded data — none is inferred from a reading.

### F1 — HIGH. `aktualizuj` skips the very entries `/zmiana` reported as changed, and reports them as refreshed

`pipeline.py:888` filters the changed identifiers through
`store.stale_detail_ids(ids, ttl_days=deps.settings.cache_ttl_days)` (default 7 days) before
asking for details. But `/zmiana` **is** the staleness signal: an entry that changed yesterday and
was fetched three days ago is dropped by the TTL filter, its pre-change `detail_json` is kept, and
the summary prints *"Zmienionych wpisów: 1, szczegółów: 1."*

`store.stale_detail_ids` (`store.py:727-743`) treats "fetched inside the TTL" as fresh
unconditionally. That is the right rule for `pobierz`, where cache reuse is the whole point, and
the wrong rule for `aktualizuj`, where the caller already knows the record changed.

Reproduced offline against the real `Store`: the second run sent **zero** requests, kept the
pre-change detail, and reported `unresolved = 0`. The `unresolved` observer cannot fire, because
the record *is* resolved — with the wrong content. Measured on the operator's own database:
**742 of 2 891 identifiers (25.7 %)** recurred between two change runs 23 hours apart.

**The causal chain is the finding, not the line.** Before 2026-09-08, ADR-0013's identifier-case
defect meant the detail cache never hit, so `stale_detail_ids` returned everything and F1 could not
manifest. **Fixing ADR-0013 activated F1.** One silent-loss defect was masking another.

**Consequence for the planned cheap proof.** The commissioning prompt proposes repeating
`aktualizuj` and treating "zero detail requests" as evidence that the ADR-0013 repair works on the
real register. After F1, **zero detail requests is exactly what the defect also produces.** That
measurement can no longer distinguish the fix from the bug, and must not be bought until F1 is
closed — or it must be replaced by one that inspects `detail_utc` rather than the request count.

### F2 — HIGH. Batched fetch silently excludes entries outside 1990-01-01…today, and the warning names the wrong cause

`batching.py:134`: `od = criteria.data_od or floor` with `DATE_FLOOR = 1990-01-01`, `do = ... or
today`. An un-dated query sends no date filter at all; the same query, once split into batches,
sends one for every batch. The split therefore changes the result set.

Measured on a real voivodeship snapshot: **3 467 of 287 256 rows (1.21 %)** start before 1990,
earliest 1957 — and a real `/firmy` record carries `dataRozpoczecia = 2026-10-05`, i.e. past
`today`. `BatchResult.missing` does detect the shortfall, but `flow.py:509` tells the operator the
missing rows are "wpisy bez daty rozpoczęcia", while that snapshot contains **zero** blank start
dates. A fixable gap is presented to the operator as an unfixable one.

### F3 — HIGH. A batched export's `Metadane` sheet describes only batch 1

`pipeline.py:1248`: `run = runs[0]`, then `build_metadata(run, …, records=<all runs>, parts=runs)`.
Reproduced with the project's own function over the operator's real runs: `liczba_trafien_count =
89` printed beside `liczba_pobranych_rekordow = 710`; `liczba_stron = 2` against 19 real pages; a
36-second `pobranie_start/koniec_utc` for a fetch that spanned days. `status_runu` and `ostrzezenie`
likewise come from batch 1 only — so an interrupted batch 7 leaves no trace anywhere in the
workbook the operator receives.

### F4 — MEDIUM-HIGH. A stale detail overrides a fresher list in the same row

`normalizer.merge_sources` (`:443`) never compares `detail_utc` against `list_utc`. Demonstrated:
an exported row read `status = 'AKTYWNY'` while that row's own `list_json` — and its `status_api`
index column — already said `WYKRESLONY`.

### Medium

- **F5** `eksportuj` without `--run-id` exports the newest run *of any status*, while its help
  promises "ostatni zakończony", and the summary does not show the status.
- **F6** A list-mode export states `liczba_pkd = 0` and `liczba_spolek = 0` as facts; the guard
  that suppresses those columns exists for the report path, not the list path.
- **F7** Report rows with neither NIP nor REGON get a `HASH:` identifier computed over `Lp.`, so
  it changes on every download — 315 rows measured.
- **F8** `report_covers` blocks only `WYKRESLONY`, but the snapshot also lacks
  `OCZEKUJE_NA_ROZPOCZECIE`; the offer warns about one of the two.

### Not settled

- **F12** `matches_criteria` uses exact match for `miasto/powiat/gmina/kod/ulica/imie/nazwisko`,
  while only `nazwa`'s server-side semantics were ever measured (substring). If any of those seven
  is substring-matched server-side, the report path silently returns a subset while a code comment
  asserts parity. Settling costs two production requests; they were not made.
- **F10/F11** `_iter_paged`'s count-guard truncation (a log line only) and `count()` falling back
  to "1" are unambiguous in the code but could not be triggered offline.

### Verified clean — so no later pass need repeat it

Identifier canonicality (0 non-canonical of 15 955), `records_seen` against `COUNT(run_firma)`
(exact for all 7 runs), `COALESCE` never erasing scalars, `_split_pkd` dropping only `N/A`,
checkpoint/record atomicity, and the atomic-replace pattern in every file write.

## Pass 3 — evidentiary value of the test suite (complete)

### Verdict on the owner's hypothesis: supported, but the statement needs sharpening

Three of the pass's own suspicions were **falsified**: the epoch-scale `approx` is properly closed
with `abs=1e-6`, `effective_spacing` is a genuine `max` and not a tautology, and the
`SSL_CERT_FILE`/`trust_env` test really does discriminate on httpx 0.28.1 (verified out of band).
The suite is unusually disciplined — planted-violation meta-tests for every boundary scan, positive
controls in the DNS-stub tests, database-level assertions on the lock lease, secret samples derived
from `SECRET_PATTERNS` by object identity.

What supports the hypothesis is the **distribution, not the count**: every place already paid for
carries exemplary evidence, and the failure shape simply migrated somewhere unpaid. The sharper
claim is that defects here come from **evidence material that was never audited against the thing it
stands for** — `registry_id` applied by convention rather than by construction, an oracle that copies
the implementation, a threshold anchored to itself, a helper exercised by calling it rather than by
reaching it. The project already invented the right instrument twice (`tests/fixtures/api_traits.yaml`,
and the cross-constant invariant test) and has applied neither to its doubles, its oracles, or the
report path.

### The strongest instances

1. **The ADR-0013 production symptom is live inside the green suite.**
   `tests/test_update_progress.py:114` passes non-GUID ids (`id-0000`) through
   `support.registry_id` (`.upper()`), which `kanoniczny_id` then leaves alone — so the `/firma`
   double answers `ID-0000` to a request for `id-0000`. Running the file's own helpers produces
   `details: 0`, every `detail_state == 'nieznaleziony'`, and **40 rows in `firma` for 20 changed
   entries** — the verbatim 2026-09-08 symptom. Three tests pass over it; none asserts that a detail
   landed.
   It also exposes an untested production door: `client.py:472-477` puts the same entry into **both**
   `found` and `missing` when the register returns an id that was not requested — and
   `store.save_details` writes details first, then marks missing, so the fetched detail would be
   overwritten by `nieznaleziony`. In production this is unreachable for real GUIDs, because
   canonicalisation makes the case difference vanish; the invariant asserted in the comment at
   `pipeline.py:559` ("`fetch_details` gwarantuje, że `found ∪ missing` pokrywa porcję") is therefore
   true by accident of canonicalisation, not by construction, and nothing checks it.
2. **`config.register_secret` is never reached through its production seam.** `config.py:445,449`
   is the only mechanism that masks an **opaque** (non-JWT) secret. Every test calls
   `register_secret` directly; every token fed through `load_settings` is either a JWT (masked by
   regex anyway) or shorter than `MIN_REGISTERED_SECRET`. **Deleting both production calls leaves
   all 999 tests green** — confirmed by mutation M1.

   **Correction to this pass, measured by the orchestrator.** Pass 3 asserted that the owner's real
   token is the opaque case, which would make this a live exposure of a PESEL-bearing credential.
   It is not: `CEIDG_TOKEN` is a JWT (`ey…`, three dot-separated segments, 317 characters) and is
   therefore matched by `SECRET_PATTERNS[0]` independently of `register_secret`; `ANTHROPIC_API_KEY`
   is matched by `SECRET_PATTERNS[1]`. `CLAUDE.md` is right about the token's shape. The finding
   stands as an untested seam for the *non-JWT fallback*; its severity does not.
3. **An assertion that cannot fail.** `tests/test_pkdmap_data.py:122` asserts
   `len(mapa) == len(czyste) + len(niejednoznaczne)`, where `TablicaPkd.__len__` returns the size of
   the very key set those two lists partition — `n == n` for any input file. Alongside it, the anchor
   constants have drifted from their own provenance prose (comment says 264 and "55 / 209";
   constants are 357 / 51 / 306) — updated to match a regenerated file, which is exactly what the
   comment forbids.
4. **The "independent oracle" certifies the blind spot.** `test_s4_hostile_data._is_safe` copies
   `ord(ch) >= 32` verbatim from `safetext.strip_control`. Measured: DEL `\x7f` — which is *in* the
   test's own `HOSTILE` list — plus C1 CSI `\x9b` and NEL `\x85` survive `sanitize_text`,
   `strip_control` **and** `richtext.safe`, and the oracle declares them safe.
5. **A threshold asserted against its own constant, still open on the report path.**
   `SCANNED_ROWS = 4 * REPORT_PAGE_SIZE` compared against `>= SCANNED_ROWS // REPORT_PAGE_SIZE`.
   Raising `REPORT_PAGE_SIZE` to 250 000 keeps the test green while a real 287k-row report emits one
   signal and one heartbeat. The waiting doctrine has a cross-constant invariant
   (`WAIT_SLICE_S < DEFAULT_LOCK_STALE_S`); the scanning doctrine has none. Relatedly, the report
   heartbeat spy records the literal `1`, so `assert beats` is satisfied by a single beat in 4 000
   rows — while the ratelimit spy records `clock.wall()` and bounds the gap.

Also found: four `/firma` doubles still echo the requested id (one of them returning lower-case ids
from `/firma`, contradicting `tests/fixtures/api_traits.yaml`); and the anonymiser truncates
`/raporty` 816→12 and `/zmiana` 100→10 without declaring it, while `test_client.py:267` asserts the
slice constant `12`.

## Pass 6 — unfinished though it looks done; survival without the author (complete)

Everything below sits **behind passing gates**: ruff, `ruff format`, mypy and 999 collected tests
were green while these were found.

### Unfinished though it looks done

**`wyczysc --starsze-niz 0` silently keeps 30 days of personal data.** `cli.py:750` reads
`days = starsze_niz or settings.retention_days`. The option is declared as a proper `int | None`
tri-state (`cli.py:690-692`), so `0` parses correctly — and then `0 or 30` makes it `30`. An
operator who asks to wipe the store is told the purge succeeded and keeps a month of sole-trader
personal data. That `0` is meaningful is proved twice inside the same function: `cli.py:741`
deliberately passes `days=0` to mean "all ZIPs", and `store.purge_older_than` handles it correctly.
The correct idiom sits fifteen lines earlier at `cli.py:166` (`if maks is not None`).
`grep -rn "starsze-niz\|starsze_niz" tests/` returns **nothing** — the flag has never been tested.

**Its twin: `--lista` cannot switch off `szczegoly: true` from a query file.** `--szczegoly/--lista`
is a plain `bool` (`cli.py:282-284`), and `cli.py:164-165` applies it only when true. So
`pobierz -z plik.yaml --lista --tak` silently fetches the *expensive* direction, and `flow.py:369`
then turns the survived value into the confirmed default in the cost table.

**The phase-5 repair has never been confirmed against the register, and the migration it needed
has already run.** The production store read read-only: `user_version=3`, 16 310 firms, 17 058
links; the log's last line is `2026-09-08T16:04:07 … 15550 zapisanych dwukrotnie (scalono w jeden)`.
`docs/status.md:1164-1169` and `.claude/sessions/2026-09-08.md:152-154` both still say schema v2
and still carry a `wyczysc` warning that no longer applies. The cheap confirmation at
`status.md:1170-1172` is still un-run, and the watermark still points at `2026-09-07T17:09:51Z`,
so it remains available.

**`ceidg_probe.py` still has the §B proxy hole that `docs/status.md:404-406` reports closed "for all
three" probes.** It uses `urllib.request.urlopen` (`:72`) with its own `time.sleep` (`:55-57`). It
is excluded from ruff (`pyproject.toml:58`) and never type-checked — `mypy scripts` yields 26
errors that nothing observes.

### Survival without the author — the three most expensive blockers

1. **You cannot obtain the code from the URL the repository points at.** `origin` is `PIWorkmate`;
   cloning it checks out `Main`, a different product. `README.md` mentions neither git, nor the
   branch, nor how to get the source. And `push.default=upstream` together with
   `branch.master.merge=refs/heads/ceidg-tool` is **local-only config that no clone carries** —
   without it, git's own hint offers `git push origin HEAD`, which would create a `master` branch
   on another team's repository. The only record of that trap is the body of commit `1791008`.
2. **There is no way to run this without real personal data, and no way to obtain a token without
   a Polish Profil Zaufany.** The default `test` environment is dead — confirmed from the data:
   2 802 `prod` requests ever, **zero** `test`. It also fails *slowly*: the retry ladder computed
   from `client.py:50-51` gives about **36 minutes** before `TransportError`, and
   `ui/texts.py:78-93` never warns that the host is known-unreachable. `profiles/test.yaml` differs
   from `prod.yaml` by exactly one line (`base_url`), and every `# sonda:` comment in it is a copy
   of the production measurement.
3. **The documented install produces a suite that cannot be collected.** `README.md:19` says
   `.[dev]`; `ci.yml:22` says `.[dev,asystent]` and explains that without the extra,
   `tests/test_assistant_caller.py:15` (a bare `import httpx2`) fails to collect and boundary rules
   11/12 lose the real import graph. `requirements.lock` pins the CI install, not the README's, and
   no document gives a command that consumes it.

Close behind: everything needed to *verify* the project's claims is gitignored (`probe_out/`,
`PKD/`), so `test_api_traits` skips its production audit, neither PKD YAML can be rebuilt, and 9 of
11 scripts cannot run from a clone.

### R1 — The headline PKD figure is wrong, and it is wrong in the direction that overstates the problem

`docs/decisions.md:103`, `docs/status.md:814` and `CLAUDE.md` all say that **25.2 %** of the register
"cannot be reached by **any** code in `pkd2025.yaml`". The sentence states one metric and the number
under it measures another.

Recomputed independently by the orchestrator from `probe_out/raport_sample.zip`
(287 256 rows, dictionary of 728 codes, secondary codes split on their real `$##$` separator):

| Metric | Records | Share |
|---|---|---|
| **A.** The record's *main* code (`GlownyKodPkd`) is not in `pkd2025.yaml` | 74 048 | **25.8 %** |
| **B.** *No code the record carries* is in `pkd2025.yaml` | 26 724 | **9.3 %** |

The documented sentence asserts B and prints A. Which metric is the operative one depends entirely
on whether the `pkd=` filter matches only the main code or any code — and that was settled from the

## Synthesis — one assessment

### The shape of this project's defects has changed, and the documents have not noticed

The tool's *logic* is in good condition. Six passes looking for it found no corruption in the
store, no loss of canonicality (0 non-canonical identifiers in 15 955), exact agreement between
`records_seen` and `COUNT(run_firma)` across all seven runs, atomic checkpoints, atomic file
replacement, and a token that appears nowhere in a 51 MB production database — zero token bytes,
zero JWT segments, zero `Bearer`.

What the passes did find clusters into three shapes, and all three are about **evidence rather
than logic**:

1. **A guard that is right, and a document that describes a different guard.** `min_spacing_s` is
   3.75 in the code and 3.6 in four documents. Schema is v3 in the code and v2 in the design
   document. The PKD gap is ~9 % in the data and 25 % in three documents including `CLAUDE.md`.
2. **A guarantee whose violation nothing would print.** The project named this doctrine itself, on
   2026-09-08, and it recurs: `register_secret` can be deleted from `load_settings` and 999 tests
   stay green; `ratelimit` can import `store` and every boundary test passes; ADR-0002's guard 3
   cannot fire at all.
3. **A fix that unmasked the defect beneath it.** ADR-0013 restored the detail cache, and in doing
   so activated F1 — `aktualizuj` now skips exactly the entries `/zmiana` reported as changed.

The third is the day's most important single finding, because it is the only one that is
**actively losing data right now**, and because it silently invalidates the cheapest planned
measurement (see F1).

### Where the passes disagreed — which no single pass could see

**On boundary rules, passes 2 and 4 reach opposite practical conclusions from compatible facts.**
Pass 4 assessed rules 1-6 and 8 as "no recorded violation" and recommended *keeping* them, proposing
a planted-import sweep to settle it. Pass 2 had already run that sweep on `ratelimit.py` — and it
**passes every boundary test**, because `ratelimit` appears in no rule at all. So the correct action
is neither "keep as ceremony" nor "remove": the rules need **extending** to cover a module
`CLAUDE.md:154` already claims is covered. Pass 4 was answering "is there history behind this rule";
pass 2 was answering "does the scan enforce what the docs claim". Both were right; only together do
they say what to do.

**On the test suite, passes 3 and 4 look contradictory and are not.** Pass 4: every test cluster
earns its keep, none is ceremony. Pass 3: several assertions cannot fail. Both hold, at different
altitudes — the suite is unusually disciplined in aggregate (planted-violation meta-tests, positive
controls, identity-derived secret samples) and has specific unpaid spots. The resolution matters for
the fix list: **do not restructure the suite; close the named holes.**

**On `client.py:472-477`, pass 3 and pass 1 differ, and pass 1 is right.** Pass 3 found a production
branch that puts one entry into both `found` and `missing`. Pass 1 measured canonicality clean and
did not flag it. Reading settles it: for real GUIDs, canonicalisation makes the case difference
vanish, so the branch is unreachable in production. It is a *test-double* artifact — but it also
means the invariant asserted at `pipeline.py:559` is true by accident rather than by construction,
and nothing checks it.

**On the owner's own two hypotheses, the passes split — one refuted, one upheld and sharpened.**

- *"The project is over-invested in documentation."* **Refuted as stated.** Code 10 551 lines,
  prose 7 146, tests **17 613**. Prose:code is 0.68:1; tests:code is 1.67:1. The largest artifact
  here is the test suite. What *is* true: 20 % of `docs/` is duplicated narrative, and the
  1 076-line retrospective log in `status.md` is the one control that can be positively removed —
  nothing reads it, and it has caused two errors elsewhere.
- *"The weakest point is the evidence material, not the code."* **Upheld**, and sharpened by the
  measurement: the defects come from evidence material **never audited against the thing it stands
  for** — a helper applied by convention rather than construction, an oracle that copies the
  implementation, a threshold anchored to its own constant. The project already invented the right
  instrument twice (`api_traits.yaml`, the cross-constant invariant test) and applied it to neither
  its doubles nor its report path.

### Would it survive without its author? No — and the blockers are cheap to remove

Three, in order of cost to a new owner: the code cannot be obtained from the URL the repository
points at (`origin` is another team's product, and the branch config that makes `git push` safe is
local-only, recorded in one commit message); there is no way to run the tool without real personal
data, and the `test` environment fails **slowly** — about 30 minutes of retry ladder before it says
the host is unreachable, with no warning that it is known-dead; and the documented install
(`README.md:19`, `.[dev]`) produces a tree whose suite cannot even be collected, because CI's
`.[dev,asystent]` is required and only the CI file says so.

The demo, if it is built to survive `git clone`, removes the second of these as a side effect. That
is the strongest argument for building it.

### Is this the right thing to build?

Partly, and the measurement says where it is not. The operator's goal is one spreadsheet of sole
traders matching a description. The tool has two paths to that, and their costs differ by four
orders of magnitude: the API path spends one request per 25-200 records at 3.75 s spacing, while
the **report path delivered 287 256 records in a single request** — the archive this audit measured
against. The report path is genuinely weaker (no per-record details — the 355 `CEIDG_RAPORT` rows in
the production store all sit at `detail_state='brak'` — a fixed column set, and status coverage gaps
F8 names). But for the shape of question this tool exists to answer, "all hairdressers in
Wielkopolska", one request beats three hours, and the machinery that dominates the codebase —
limiter, batching, resume, cost tables — is machinery the *report* path barely needs.

This is not an argument to delete the API path: details are exactly what makes the workbook worth
having, and `aktualizuj` has no report equivalent. It is an argument that **the report path deserves
the polish currently going to the API path** — and today it is the path with the unfixed identifier
instability (F7), the wrong status warning (F8), the unobserved heartbeat threshold, and no resume
at all.

### Verdict

The code is better than its documentation, the test suite is better than its weakest assertions,
and the single thing standing between this tool and being trustworthy is that **`aktualizuj`
currently keeps stale data and reports it as fresh**. Fix F1 first; everything else on the list is
smaller than it.

## Stage 1 — A1 closed (`aktualizuj` no longer keeps stale data)

**What changed.** The freshness threshold is supplied by the caller and equals the end of the
`/zmiana` window, replacing the cache TTL that `store.stale_detail_ids` computed for itself.
A repeat of an already-processed window still costs zero detail requests, because `detail_utc >=
window_end` holds. `store.outdated_details` observes violations per window; `RunResult.stale_details`
carries the count of **distinct entries**; the summary says so, and each window with a non-zero
count also emits an `on_message`, so the alarm reaches the log file rather than only the terminal.
`update_range` refuses a range that ends in the future or is empty, on all three of its start
branches; `cli._koniec_zakresu_zmian` refuses the same earlier with a friendlier message, and takes
its "now" from the injected clock so there are not two different nows in one command.
`set_watermark` is now monotonic. `aktualizuj --do` exists.

**Evidence.** 28 new tests in `tests/test_update_freshness.py`, every one verified by breaking the
mechanism it covers and confirming it reddens. Two results are worth recording because they are the
audit's own doctrine in miniature:

- "the stale count is zero after a correct run" stays **green** when the TTL defect is reintroduced
  *and* the counter deleted together — zero after a correct run is indistinguishable from zero
  nobody computes. That is why a separate test injects the regression at the seam
  (`stale_detail_ids` returning `[]`, exactly what a 7-day TTL did for a 3-day-old detail) and
  asserts the alarm rings, the pre-change name is still in the database, and `unresolved` stays
  silent.
- "a range ending today is accepted" stays green when the future-guard is deleted, by design: it is
  the guard against an over-strict guard, and it dies under the opposite mutation.

**What the review caught in the fix itself.** Six findings, all applied. The observer was blunter
than the rule it watched (per-run threshold against a per-window filter); the range guard covered
one start branch of three, so `--od 09-05 --do 09-05` and a `--do` earlier than the invisible
watermark both produced "Baza jest aktualna" with no request sent; `--do` in the past rewound the
watermark; the count summed window occurrences while the sentence said entries; and three
docstrings still described a clamp from an abandoned draft — the same evidence-shaped-like-proof
pattern this audit is about, caught inside the change that was fixing it.

**Sixth instance of the fixture shape.** Six places in the suite paired the `conftest` clock
(epoch 2023-11-14) with change windows in 2026. The old TTL threshold read "seven days back from
now" and never looked at the window, so the inconsistency was invisible for the whole life of those
tests. Under the new rule a clock before the window means "the detail must come from the future",
and the range guard now rejects it outright. The clocks were corrected, not the assertions.

Gates after the stage: 1027 tests, mypy strict over 98 files, `ruff check`, `ruff format --check` —
all green.

### Three defects the review found in the demo, all one shape

Each is reference data written from memory, which passes every automated check because nothing
checks it — the same shape as the audit's own recurring finding, committed fresh inside the change
that was fixing it.

1. **PKD names were invented.** `5610A` and `8690E` were declared as PKD 2025 codes and do not exist
   in PKD 2025 at all; three names disagreed with the dictionary. This is the trap `CLAUDE.md` names
   as the project's worst, because the operator's only control is the PKD *name* on the confirmation
   screen — a fabricated name makes the screen agree with the mistake. Fixed by removing every name
   from the module: it now declares code pairs only, reads both vintages from the generated
   dictionaries, and refuses to build if a code is absent **or if the pair is not a real 2007→2025
   succession** (the second check added because pairing `9602Z → 6210B` would otherwise pass).
2. **Four of five city/powiat pairs were wrong.** A city with county rights files under `powiat`
   equal to its own name; the project's own fixtures show `Kalisz` with powiat `Kalisz` while
   `kaliski` belongs to a village. An operator learning the pattern from the demo would write a
   production query that returns nothing.
3. **The `/firmy` record was poorer than the register's.** Measured over 196 real list records,
   `/firmy` carries the full `wlasciciel`, a `link` and a complete address (empty in 76 of them).
   The demo returned two address fields, so it argued *for* paying for details on evidence the
   register does not support — inverting the very decision the demo exists to stage.

Also fixed from the same review: `eksportuj --demo` built its deps without the demo flag, so a
re-exported workbook lost two of the five markers; `--out` bypassed the filename prefix;
`CEIDG_DEMO_TEMPO` had no upper bound and failed by blaming the system clock; the corpus identifier
ignored the seed; the register double compared filters case-sensitively where the register is
measured case-insensitive.

**Tests: 96 across four files, each verified by breaking what it covers.** Four could not fail and
were repaired — the sharpest being the credential tests, where `env_file=None` and
`use_keyring=False` had **no observer at all**, because `token=` outranks both and a test checking
only the resulting token value passes while `.env` is being read.

## Stage 3 — the fresher source wins (A5)

`merge_sources` let the detail override the list unconditionally, without comparing when each was
fetched. That is right while the detail is younger and false when it is not — and it is routinely
not, because details sit in a cache while `pobierz` refreshes the list on every run. Measured
symptom: an exported row read `status = 'AKTYWNY'` while that row's own `list_json`, and its
`status_api` index column, already said `WYKRESLONY`. The workbook contradicted the data it was
built from, and nothing said so.

The rule is now "the fresher source wins on shared fields, the older one still fills gaps", with
`None` still meaning "unknown" rather than "empty" — the same rule as before, on the correct side
of the comparison. Where either timestamp is missing there is nothing to compare and the previous
order stands.

Five tests, mutation-checked: restoring the old rule reddens the two that name the symptom
(including the one that goes through `normalize` to the actual spreadsheet row) while the three
positive controls stay green — among them the one pinning that a fresher list must not erase
`rokPkd`, which the list does not carry. Without that control the fix could have been the same
defect turned 180 degrees.

### Code review of stages 4-8 — twelve findings, all applied

The review confirmed all six fixes correct for every case it could reach, and found twelve things
the four gates cannot see. Two are worth recording beyond the fix itself, because both are this
project's own doctrine catching the batch that was applying it:

- **Two new observers had no test at the wiring layer.** Deleting `statuses=summary.statuses` and
  the surplus note from `ui/flow.py` left **all 1182 tests green**: both values were computed
  correctly and neither was delivered. That is A7's own shape — a value computed and not carried —
  reproduced inside the change that was fixing A7. Both now have tests that go through
  `export_and_report` and `_run_batches` to the rendered block, and both were mutation-checked.
- **Opening the last edge made its fingerprint permanent**, so a repeat `pobierz --partie` of an
  undated query skipped every batch as "already fetched" and returned nothing new — while the
  un-batched path always refetches. The old `data_do = today` had been hiding this by changing the
  fingerprint daily. Resolved by a distinction that is true rather than convenient: a **closed**
  tile is a population that cannot grow, an **open** one grows with every new registration, so
  `run_batched_fetch` skips a completed batch only when its upper edge is closed. Recorded in
  ADR-0015.

The other ten: the `|` separator in `id_z_tresci` was a legal character in a registry name, so the
field boundary was steerable by hostile input and `("A|B", "C")` collided with `("A", "B|C")` — the
digest is now a function of the tuple, as ADR-0016 measured it; the offer screen restated
`STATUSY_SPOZA_RAPORTU` in prose, so a third status would have been refused and not named (a cross-
constant test now guards it, since `texts` must stay pure); `no_finished_run` counted `list_runs()`,
reporting the **page size** as the number of runs in the database; `wersja_narzedzia` and
`profil_api_hash` still came from part 1; the `HASH:` prefix was hardcoded in `pipeline`;
`list_runs(statuses=...)` accepted a bare `str` that mypy could not object to; plus four
documentation slips, including an attribute docstring this change had displaced onto the wrong
field and a blockquote that swallowed the paragraph after it.
