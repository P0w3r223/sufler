2. Dlaczego w tej kolejnoci

Zaczynamy od Claude Code, bo to najkrótsza droga do dzialajcego dowodu: adnego agenta w rdzeniu,
czysto MCP, a przy okazji wykuwamy kontrakt narzdziowy, na którym stanie reszta. Gdy ten kontrakt si
ustabilizuje, doloenie Teamsa i GitHuba jest ju tylko dokladaniem drzwi.

Jest jednak asymetria, któr warto zobaczy od pocztku: Claude Code chce narzdzi, a pozostale drzwi
chc agenta. Claude Code sam w sobie jest agentem -- potrzebuje tylko narzdzi, i do tego MCP jest
stworzone wprost. Ale Teams i GitHub nie maj wlasnego modelu w ptli, wic dla nich to rdze musi
dostarczy agenta: model, który czyta zapytanie, wola te same narzdzia i sklada odpowied. Te same
narzdzia pod spodem, dwie róne glbokoci wejcia -- i to jest powód, dla którego Faza 1 jest tasza ni
Faza 2.

3. Zasady przekrojowe (obowizuj we wszystkich fazach)

 · Wskie, typowane narzdzia -- adnego ,,czytaj dowolny plik" ani uruchamiania powloki. Kade
   narzdzie ma jasno okrelone wejcie i wyjcie.

 · Sekrety i klucze poza zasigiem rdzenia -- id do menedera sekretów, a nie do folderu, który rdze
   indeksuje.

 · Tre niezaufana = dane, nie polecenia -- notatki i transkrypty mog zawiera tekst udajcy
   instrukcj. Narzdzia traktuj pobran tre jak dane; nie wykonuj polece w niej znalezionych.

 · Struktura przy zapisie, nie przy odczycie -- kada notatka w stalym szablonie i stalym schemacie
   folderów. To ta jedna rzecz, która czyni odpytywanie i ledzenie stanu proste.

 · Profil uprawnie per drzwi -- ten sam mózg, ale issue na GitHubie jest mniej zaufane ni
   uwierzytelniona sesja deva. Ta sama akcja z mniej zaufanych drzwi wymaga mocniejszego bramkowania.

4. Trzy bramki decyzyjne (nale do zespolu)

Kod nie jest tu najtrudniejszy -- najtrudniejsze s trzy decyzje projektowe. Praktykant je przygotowuje;
zatwierdza je zespól na synchronicznym przegldzie, zanim praktykant ruszy dalej.

   Bramka 1 -- kontrakt narzdzi + schemat notatki (koniec tyg. 2)
   Nazwy narzdzi, ich wejcia/wyjcia oraz staly schemat notatki: projekt, data, uczestnicy, decyzje, action itemy,
   otwarte pytania. Po zablokowaniu tego, reszta staje si rozbudow.

   Bramka 2 -- granica uprawnie, sekrety, tre niezaufana (koniec tyg. 3)
   Co rdze moe czyta, a czego nie; gdzie le sekrety; jak traktowana jest tre niezaufana. Duy, wspólny
   przegld -- przed dotkniciem czegokolwiek realnego.

   Bramka 3 -- wdroenie i dostp (koniec tyg. 4)
   Sposób uwierzytelniania per osoba, uprawnienia minimalne, dystrybucja konfiguracji do zespolu -- przed
   pójciem na ywo.

5. Faza 1 -- Integracja Claude Code (MVP) tyg. 1-4

Cel fazy: hostowany serwer MCP na serwerze firmowym, który daje Claude Code kadego deva dostp
do wspólnej bazy wiedzy -- notatek i statusu projektów (mpwik, biap). Dev pyta w terminalu ,,co
ustalilimy z mpwik w sprawie X" i dostaje odpowied opart o nasze notatki.

Zakres -- wiadomie glównie do odczytu: narzdzia search_notes, get_note, list_projects,
get_project_status. Bez RAG-a (to póniej) -- na start zwykle wyszukiwanie po metadanych nad dobrze
uschematyzowan notatk. Jest realne dla juniora w 4 tygodnie i naprawd uyteczne.

Stack: Python, oficjalny pakiet mcp[cli] z wysokopoziomowym interfejsem FastMCP; uv do rodowiska;
MCP Inspector do testów; Claude Code jako klient (dodanie przez claude mcp add, konfiguracja zespolowa
w .mcp.json w scope project wrzuconym do repo).

6. Faza 2 -- Teams + runtime agenta tyg. 5-8

Cel fazy: doloy pierwsze drzwi asynchroniczne. To wymaga dostarczenia agenta w rdzeniu -- ale narzdzia zostaj
te same co w Fazie 1. To jest caly sens wczeniejszego dopieszczenia kontraktu.

M1 -- Runtime agenta w rdzeniu.
    Model (np. przez API Claude), który dostaje zapytanie w jzyku naturalnym, ma dostp do tych samych narzdzi
    co Claude Code, decyduje, które wywola, i sklada odpowied. Rdze dostarcza rozumowanie tam, gdzie nie ma
    Claude Code.

M2 -- Adapter Teams.
    Aplikacja bota (Bot Framework / Microsoft Graph) reaguje na @wzmiank, przekazuje tre do runtime agenta
    i odsyla odpowied do wtku.

M3 -- Przeplyw ,,nowa notatka ze spotkania".
    @WorkMate nowa notatka  pobranie transkryptu przez Graph  streszczenie wg zablokowanego schematu
     zapis do wlaciwego folderu projektu. To realizacja pierwotnego marzenia.

M4 -- Twarde tematy asynchroniczne.
    Model zada w tle (wrzu-i-id + callback zamiast synchronicznej odpowiedzi); mapowanie tosamoci
    (Entra/AD  jeden model uprawnie rdzenia); cieka zapisu z bramkowaniem -- bo skoro Teams pisze
    na dysk, uprawnienia i tre niezaufana wchodz na serio.

   Co praktykant realnie zaczyna w tyg. 5-6: fundamenty runtime agenta (M1) oraz pierwszy spike adaptera
   Teams (M2: @wzmianka  odpowied na istniejcych narzdziach). Pelne M3-M4 to kontynuacja -- przez
   zespól lub przedluon praktyk.
